# AI辅助开发与人机协作记录

## 一、AI使用背景与总体思路

本项目选择考核题目3“企业知识问答Agent”，目标是构建一个能够根据企业制度文档提供可靠回答、识别资料冲突、主动调整检索策略，并对决策过程进行追溯的Agent系统。

在项目开发过程中，我将AI作为辅助分析、工程实现和质量验证的工具，采用了“**人工定义目标与约束—AI辅助设计方案—Codex执行开发—基于实际结果进行评估—反馈迭代优化**”的协作方式。

考虑到考核既关注可运行的工程成品，也强调对业务问题的理解、技术取舍和主动改进能力，我没有直接要求AI一次性生成全部代码，而是先分析任务的核心验收条件，再围绕技术深度、功能完整性、稳定性和可复现性组织开发。

我的主要参与集中在需求拆解、架构方案选择、功能优先级安排、验收指标制定、异常结果分析、迭代方向判断和最终交付审核。具体代码编写、工具接入、自动化测试执行及大量调试工作由Codex辅助完成。

整个过程中，我特别关注两个问题：一是如何避免AI生成的项目只有表面上的功能完整性，缺乏真正可验证的技术实现；二是如何让AI生成的每一项重要结果都能够通过代码、运行记录和测试证据进行核查。

## 二、AI工具使用及职责划分

本项目主要使用ChatGPT、Codex和通义千问Qwen-plus，分别承担不同职责。

| 工具 | 主要用途 | 使用方式 |
|---|---|---|
| ChatGPT | 需求分析、技术方案讨论、开发任务拆分、质量评审辅助 | 通过多轮对话比较方案、分析问题、形成可执行开发要求 |
| Codex | 代码实现、项目配置、测试执行、问题修复和文档生成 | 根据开发规格操作本地文件与终端，分阶段产出工程文件和验证工件 |
| Qwen-plus | EvidenceFlow运行时的真实大模型决策 | 根据用户问题和工具返回结果，动态选择检索、阅读、查证或提交答案 |
| MockModel / ScriptedModel | 离线流程验证与受控异常测试 | 验证工具接口、状态流转和错误处理，不代替真实LLM决策证据 |

在使用过程中，我有意识地区分“辅助开发的AI”和“项目运行时的AI”。

Codex负责辅助构建Agent系统，而Qwen-plus是实际运行过程中进行工具选择的模型。项目是否满足ReAct要求，必须通过Qwen-plus真实调用工具、观察结果并调整动作来证明，不能仅凭Codex生成的代码或预设执行记录判断。

## 三、人机协作开发过程

### 3.1 第一轮交互：明确业务目标与考核要求

项目启动阶段，我首先借助ChatGPT分析考核说明中的四个备选题目，从开发复杂度、时间限制、技术展示空间和验收可操作性等方面进行比较，最终选择企业知识问答Agent。

在这一阶段，我关注的核心问题是：如何在较短的开发时间内，完成一套真正具有Agent自主决策能力、又具备一定工程和算法深度的系统。

经过讨论，我将项目成功标准划分为三个层次：

**第一层：满足题目强制验收。**

实现明确答案、资料冲突、资料外问题、相似问题改写、上下文追问和工具失败六类场景，并提交真实输入、输出和运行Trace。

**第二层：证明Agent具备真实动态决策能力。**

要求模型能够自主决定检索、读取文档、核查版本、补充查询或者结束，而不是由程序根据问题内容使用固定条件分支选择工具。

**第三层：提升项目技术深度。**

增加混合检索、证据校验、冲突检测、运行可观测性和定量评估，使项目不仅能够回答问题，还能够解释为什么回答、为什么拒答以及为什么继续调用工具。

这一轮交互的主要成果是确定项目范围，并把原题中相对抽象的能力要求转化为可测试的功能目标。

### 3.2 第二轮交互：主动调整技术架构

最初讨论的方案是使用原生Python、本地JSON知识库和简单CLI，以尽可能低的实现成本完成基本流程。

我认为这种方案虽然能够满足最小验收要求，但对Agent框架、检索算法和工程能力的展示不足，因此进一步提出：希望在保证稳定性的前提下增加项目深度，而不是只完成一个简单Demo。

在与AI讨论向量数据库、LangGraph、FastAPI、前端和多Agent方案后，我逐步明确了技术选择：

- 使用LangGraph StateGraph管理Agent状态与决策循环。
- 使用BM25、Dense Retrieval与RRF构建混合检索体系。
- 增加EvidenceGuard约束引用和答案。
- 实现制度版本及适用范围冲突检测。
- 使用FastAPI提供接口，Streamlit负责交互和Trace展示。
- 保留Evidence Critic作为进一步增强的可选模块。

在技术取舍上，我没有要求系统尽可能多地使用框架。例如，对于规模较小的合成制度库，没有单独引入大型向量数据库服务；对于当前任务，也没有强行拆分多个Agent。

我希望每个新增技术模块都能回答一个具体问题：它解决了什么业务或工程缺陷、增加了什么能力，以及能否通过实验验证其价值。

这一阶段形成了EvidenceFlow整体技术架构和功能边界。

### 3.3 第三轮交互：将自然语言需求转化为可执行开发规格

明确架构后，我没有直接要求Codex自由发挥，而是继续与ChatGPT细化开发任务。

我要求方案必须包含完整业务背景、系统架构、模块职责、数据设计、输入输出格式、每一步的实现目标以及可执行的验收标准。

在此基础上，将项目拆分为P0至P8多个阶段，包括环境初始化、知识库与工具实现、动态决策、证据校验、官方场景验收、检索增强、前后端开发、Critic扩展和最终交付。

我重点增加了以下约束：

1. 每个阶段完成后必须执行实际检查，不能仅根据代码存在就判定通过。
2. 每项重要功能要对应自动化测试或真实运行证据。
3. 验收状态必须区分PASS、FAIL和BLOCKED。
4. 发生失败后保留原始记录，修复后重新执行测试。
5. 不允许通过修改测试用例、降低验收阈值或删除失败记录制造通过结果。
6. Mock测试与真实模型测试必须明确区分。
7. 项目必须设置执行次数上限，防止Agent无限循环。

随后将开发规格、总控提示词、验收关卡配置和原始题目一并交给Codex。

这种方式使Codex能够基于明确的任务契约连续开发，也使后续审查有了统一依据。

### 3.4 第四轮交互：实际运行环境配置与问题处理

开发过程中，我参与了真实运行环境的配置和问题排查。

**模型接入方面：**

我根据Codex的环境要求，在本机配置LLM_API_KEY、LLM_BASE_URL和LLM_MODEL_NAME，并通过讨论区分模型平台的普通API地址与OpenAI兼容接口，最终接入Qwen-plus。

模型凭证只在本地配置，没有在聊天内容中传递真实密钥，也没有将本地.env作为项目材料提交。

**GitHub环境方面：**

在配置GitHub CLI时，我遇到了PowerShell命令解析错误和gh.exe路径无效的问题。经过逐步检查，修正命令格式并重新确认GitHub CLI的安装与登录方式，继续推进仓库交付。

**前端运行方面：**

首次尝试运行Streamlit时，8501、8502端口均提示不可用。

我先使用PowerShell检查监听端口，再运行Windows端口排除范围查询，确认系统保留了8494–8593等多个TCP端口段。由此判断问题与端口保留机制有关，后续改用未被排除的端口，并要求在README中同步修订启动说明。

这一过程让我认识到，AI辅助开发中出现的错误不一定来自业务代码，还可能来自操作系统、运行环境或工具配置。解决问题时应先收集可观察证据，再确定修改范围，避免没有依据地重装环境或重构项目。

### 3.5 第五轮交互：多次审查交付结果并提出修改要求

Codex生成第一版交付包后，我没有直接结束开发，而是继续利用AI辅助审查实际代码、测试记录和运行Trace。

我特别检查了以下方面：

- LangGraph是否真正调用模型决定工具，而不是通过预设条件分支模拟决策。
- 六项官方验收是否对应真实live执行。
- Trace中的工具参数、Observation与后续动作是否能够相互对应。
- 文档冲突场景是否同时引用两份资料。
- 资料不足时是否出现无依据回答。
- 自动化测试和最终报告的统计是否一致。
- GitHub中的文件是否与本地交付一致。

通过第一轮审查，发现了几个值得继续改进的问题。

其中，TC02冲突场景曾多次因为结构化答案格式不符合EvidenceGuard约束而被拒绝；部分Trace中的decision_basis描述比较模板化；此外，虽然项目实现了Hybrid RAG实验，但仍需要证明真实Agent能够使用该检索策略完成完整验收。

针对这些发现，我提出新的修改要求，让Codex分别优化结构化提交、完善决策记录，并执行Hybrid模式下的真实live测试。

这里采用的迭代原则是：**根据可复现的问题提出最小范围的修改要求，并使用相同验收标准重新验证。**

### 3.6 第六轮交互：针对冲突处理稳定性进行定向优化

在企业制度问答场景中，资料冲突是最重要的风险之一。

参考题目中D01规定30天、D02规定15天的情况，我明确要求系统不能简单选择较新的文件，也不能在没有充分依据时推断其中一份制度具有更高优先级。

在检查TC02实际运行Trace时，发现模型已经正确读取了两份资料，但最终提交的答案可能因为固定状态后缀或换行格式不符合约束而被EvidenceGuard拒绝。

这意味着问题主要集中在模型结构化输出与校验接口之间的契约，而不完全是检索能力不足。

根据这一发现，我要求Codex分析Guard拒绝的具体错误，调整提交接口与格式处理方式，同时保持原文引用、冲突识别和状态校验规则不变。

修复后，对同一冲突场景连续执行5次真实模型测试，记录每次运行状态、Guard拒绝次数和实际Trace。

项目报告记录最终5次全部通过，且没有首次提交拒绝。该结果说明指定测试条件下的输出稳定性得到改善，但不代表所有可能的复杂制度冲突都已解决。

这轮迭代体现了我对AI输出错误的处理思路：先判断错误属于检索、推理、接口约束还是最终格式，再选择对应的技术修复方案。

### 3.7 第七轮交互：从功能验证转向量化实验

基础功能完成后，我进一步要求Codex对检索算法进行定量评估。

我希望项目能够回答的不只是“混合检索能否使用”，还包括“相比传统检索究竟改善了什么，以及是否值得增加计算成本”。

因此，我要求在相同数据集上比较BM25、Dense Retrieval、Hybrid RRF以及Hybrid结合Agent动态查询改写的效果。

本项目使用32篇合成制度、44条评估问题，其中40条具有可回答依据，主要比较Recall@3、Recall@5、MRR@5、调用次数与延迟。

实际结果显示：

| 检索方法 | Recall@3 | MRR@5 |
|---|---:|---:|
| BM25 | 0.9250 | 0.9175 |
| Dense Retrieval | 0.9750 | 0.9625 |
| Hybrid RRF | 0.9875 | 0.9833 |
| Hybrid + Agent Rewrite | 0.9875 | 0.9833 |

在该测试集上，Hybrid RRF相对BM25取得了更高的检索指标，但引入Agent动态查询改写后，并没有进一步提高Recall@3或MRR@5，同时增加了模型调用和延迟。

我认为这个负面结果同样重要，因此要求保留真实实验数据，不因结果未达到预期而调整测试集或只报告表现较好的指标。

这也体现了我对AI辅助实验的基本要求：**实验用于检验技术选择，而不是为预先选定的技术寻找有利证据。**

### 3.8 第八轮交互：引入Evidence Critic并分析收益与代价

在实现严格EvidenceGuard后，我继续考虑一个问题：引用片段本身合法，是否就意味着答案已经覆盖用户问题需要的全部信息？

为处理证据遗漏、回答不完整等情况，我要求增加可选的Evidence Critic模块，对候选回答进行独立检查，并在发现证据覆盖不足时反馈给主Agent修正。

同时，我明确要求Critic不能无限循环，也不能因为增加一个审核模块就突破原有的模型执行预算。

Codex据此增加了受控修正流程，并通过故障注入评估其效果。

项目记录显示，在4个显式注入证据覆盖缺失的案例中，开启Critic后成功修正4个；另外2个正常对照未发生误修正。Critic也引入了额外模型步骤、Token消耗和响应延迟。

开发过程中，Critic最初也曾出现冲突场景修正失败以及结构化结果不一致的问题，因此又进行了反馈信息和预算管理方面的修复。

我没有将这个小规模受控测试的结果解释为模型在所有真实场景下的自我修正成功率，而是把它作为模块有效性的初步证据，并保留了成本和能力边界。

### 3.9 第九轮交互：最终交付审查与质量控制

项目完成主要功能后，我将交互重点转向最终交付质量。

我要求Codex再次检查项目结构、必需文档、真实输入输出、Trace、自动化测试、安全信息及GitHub提交一致性。

在多次交付包审查过程中，重点确认：

- README、源码、测试、合成数据及五份考核文档齐全。
- 六项官方验收都有对应的真实输入、输出及Trace。
- 真实模型与Mock记录没有混用。
- 文档修改实验能够使答案依据新原文改变。
- 失败运行记录没有被删除或改写。
- 交付文件没有包含真实模型API密钥。
- GitHub的最终提交SHA与远程分支对应。

在最后的审查中，还发现早期Git历史对象保留了本机路径信息。尽管当前文件已做脱敏，且扫描没有发现真实API密钥泄露，但历史路径隐私问题仍被如实记录为待处理事项。

这一阶段让我更加重视AI生成工程的可追溯性。项目功能通过测试只是交付的一部分，运行说明、实验记录、敏感信息处理和版本一致性同样影响最终成果的可信度。

## 四、我在提示词设计与AI使用上的主要方法

回顾整个开发过程，我逐渐形成了以下几项实践方法。

### 4.1 先定义可验证的结果，再要求AI生成实现

对于动态决策、异常恢复、资料冲突等核心需求，我尽量明确规定输入条件、预期行为、最终状态和对应证据。

例如，对于工具失败场景，要求真实模型接收到工具超时Observation后自主决定下一步，而不是简单要求AI“实现可靠的重试机制”。

这样可以减少AI生成看似合理、实际却不满足题目要求的实现。

### 4.2 将大任务拆分为有验收关卡的阶段

我要求Codex按P0至P8分阶段开发，每一阶段完成后运行实际测试，再继续后续工作。

相较于一次性生成全部系统，这种方法更容易定位问题，也能够避免后续功能建立在尚未通过验证的基础模块之上。

### 4.3 利用真实工具反馈控制迭代

我要求Codex保留运行命令、退出码、错误信息、JUnit结果、模型Trace等可观察证据。

遇到问题时，优先根据错误发生的位置和实际返回结果判断原因，而不是直接要求AI重新生成整个模块。

TC02答案格式修复、Streamlit端口排查和Hybrid检索专项验证，都是通过这种方式逐步完成的。

### 4.4 将模型的自主性与程序的安全边界分开

对于Agent系统，我认为需要明确区分模型可以自主决定的行为和必须由程序强制保证的规则。

模型负责选择下一步动作，包括检索、阅读、补查和提交答案；程序负责检查引用原文、制度冲突、工具参数、模型执行预算以及最终任务状态。

通过这种分工，可以保留Agent的动态决策能力，同时降低无依据回答和错误引用的风险。

### 4.5 不把AI生成的结论直接当作实验事实

在要求Codex产出结果时，我特别强调：

- 测试结果必须来自实际执行。
- 模型不可用时不得用Mock冒充live。
- 未测量的指标不能自行补充。
- 失败案例必须保留。
- 实验结论需要说明测试数据规模和适用范围。
- 新增模块必须说明收益及额外成本。

因此，项目既保留了Hybrid RAG的正向改进结果，也保留了Query Rewrite未进一步提升检索指标的实验结果。

## 五、人工参与内容与验证边界

本项目中的人工参与主要体现在项目目标设定、任务约束、技术取舍、开发规格制定、问题反馈、验收标准设计以及交付结果复核。

具体来说，我负责决定项目应该实现哪些能力、选择哪些技术方向、什么样的结果可以视为合格，以及发现问题后应优先修复什么。

Codex负责根据这些要求实现代码、执行测试并生成报告。ChatGPT主要辅助我进行需求分析、问题定位、方案比较和结果检查。

我没有将AI生成的代码全部表述为个人手写成果，也不将AI执行的自动化测试表述为本人逐项手工完成的测试。

在验证方面，我结合实际项目的运行日志、测试文件、模型Trace以及多轮交付包审查结果判断系统的实现情况。对于没有独立验证的部分、无法完全证明的指标及未解决的安全限制，均在相关报告中保留说明。

这种协作方式的核心在于：人负责定义问题和判断质量，AI负责提高执行效率，最终结论仍必须接受实际运行证据的检验。

## 七、总结与反思

通过这次项目，我对AI辅助软件开发的理解发生了进一步变化。

在项目早期，我主要关注AI能否快速生成代码。随着开发推进，我逐渐将关注点转向如何提出更精确的需求、制定可检验的验收标准，以及根据真实反馈指导AI改进。

尤其是在动态决策、冲突检测和证据校验等模块中，仅通过提示词要求模型遵守规则，并不足以证明系统可靠。必须进一步通过程序约束、可观察运行记录和针对性实验验证系统行为。

我也认识到，增加技术模块并不必然带来更好的效果。例如，Hybrid RAG在本次合成数据集上取得了检索指标提升，但Agent查询改写没有带来进一步收益；Evidence Critic能够修正部分受控缺失，却增加了响应成本。这些结果帮助我从单纯追求功能丰富，转向更加关注技术投入与实际收益之间的关系。

本项目中，我没有把AI作为完全自主交付的黑盒，而是持续通过需求约束、技术讨论、阶段验收、问题反馈和结果审查参与开发过程。

对我而言，这次考核最重要的学习成果，是逐步形成了一套更系统的AI协作方法：**以业务需求确定方向，以结构化任务组织AI执行，以可复现的测试验证结果，以真实的失败反馈推动改进，并在最终交付时明确能力边界和责任归属。**

后续如果继续完善EvidenceFlow，我会优先扩大独立标注的知识问答测试集，进一步验证复杂文档冲突、不同制度适用范围和更长文档中的证据支持关系，同时改进运行安全与交付流程。
